### Site summary

```json
{
  "id": "site-id",
  "name": "Example Site",
  "lat": 27.0,
  "lon": -82.0,
  "risk_score": 0.0,
  "risk_level": "low",
  "updated_at": "ISO-8601 timestamp",
  "assigned_team": null,
  "active_alerts": 0,
  "top_factors": [],
  "data_completeness": 1.0,
  "model_version": "string"
}
```

`risk_score`, `risk_level`, and `updated_at` are `null` until the site has a computed score. Show null as "Not scored yet", never as low risk. `GET /api/sites` lists assigned sites first, then scored sites by `risk_score` descending, then unscored sites, then by name. `GET /api/sites/{id}` returns `SiteDetail`, or 404 for an unknown ID.

```text
fetch(sites, now) -> list[Observation]
  # each Observation: source, hazard_type, value, unit, lat, lon,
  #                   observed_at, valid_at, data_state

lightning.submit_strike(lat, lon, time, simulated) -> Observation
  # used by the replay fixture and by tests
```

`hazard_type` is one of `weather`, `forecast`, `flood_alert`, `flood_gauge`, `lightning_strike`, `hurricane`, or `earthquake`. `data_state` is one of `observed`, `forecast`, `simulated`, `stale`, or `unavailable`. Rudra's alert rules and scoring read only these Observations and never call a feed directly. Broken electrical poles, downed lines, on-site fires, and other on-site hazards have no adapter. They arrive only through crew reports.

NWS conventions:

- Weather and forecast Observations carry one metric each. `label` is one of the constants in `nws_weather.METRIC_LABELS`: `Temperature`, `Relative humidity`, `Heat index`, and `Precipitation probability`. Temperatures are in °F.
- A successful flood-alert fetch with no active alerts returns one `flood_alert` Observation with `value=None` and `label="No active NWS flood alerts"`. A failed fetch returns `data_state="unavailable"`. Never read an empty list as "no flood."

Lightning, hurricane, earthquake, and flood-gauge conventions (T045–T045D):

- Every "none found" reading has `value=None`. Event readings carry the event's own `lat`/`lon`, so rules compute distance themselves. Each feed's search radius (`*_SEARCH_RADIUS_MILES` in `IngestionSettings`) only limits which events reach a site. It is wider than the rule distances and is not a rule setting.
- `lightning_strike` (`lightning.py`): `value` is the distance to the site in miles, and `observed_at` is the strike time. `submit_strike(lat, lon, time, simulated=True)` normalizes a strike, and `replay_strike(site, step, at)` replays `fixtures/lightning_replay.json`. Replayed strikes are `source="lightning-replay"`, `simulated=True`, `data_state="simulated"`. Live strikes come from NOAA GOES GLM (`glm.py`, background poller started by the first `fetch()`, `LIGHTNING_LIVE_ENABLED`) as `source="GOES GLM"`, `simulated=False`, `data_state="observed"`. GLM reports total lightning, including in-cloud flashes, at about 8 km resolution and 20–60 s delay. The "no strikes" reading is `GOES GLM`/`observed` only while GLM coverage is gap-free and states the minutes watched. Otherwise it is labeled simulated with the reason (not enabled, starting, unavailable). The 10-mile stop-work rule belongs to Rudra.
- `hurricane` (`hurricanes.py`): `source="NHC"` readings are active storms with `value` = intensity in kt and `lat`/`lon` = storm center. `source="NWS"` readings have `value` set to `Hurricane Warning`, `Hurricane Watch`, `Tropical Storm Warning`, or `Tropical Storm Watch`. The two sources are cached separately.
- `earthquake` (`earthquakes.py`): `value` is the magnitude, `unit` is the USGS magnitude type, `lat`/`lon` is the epicenter, and `observed_at` is the origin time.
- `flood_gauge` (`flood_gauges.py`): `label` starts with `Gage height` (ft) or `Streamflow` (ft3/s), and `source_ref` is `USGS-{site number}`. Gauges give readings, not flood stages, so NWS flood alerts remain the flood source.

#### Adding a feed adapter

All feed adapters are now maintained by Braydin and follow the existing pattern in `nws_weather.py` and `nws_alerts.py`. Write a `fetch_site` for one site and let `FeedCache` handle freshness:

```python
from datetime import datetime

from app.ingestion import FeedCache, FeedError, SiteLike
from app.ingestion.settings import get_ingestion_settings
from app.schemas import HazardType, Observation

settings = get_ingestion_settings()
cache = FeedCache("USGS", HazardType.EARTHQUAKE, settings.stale_after, settings.unavailable_after)


def fetch_site(site: SiteLike, now: datetime) -> list[Observation]:
    """Fresh readings for one site. Raise FeedError when the source gives nothing usable."""
    ...


def fetch(sites: list[SiteLike], now: datetime) -> list[Observation]:
    return [o for site in sites for o in cache.refresh(site, now, fetch_site)]
```

`FeedCache.refresh` stamps `fetched_at` on success. On any exception, it returns the last readings marked `stale`, or an `unavailable` placeholder when nothing is cached or the cache is older than `FEED_UNAVAILABLE_AFTER_MINUTES`. `FeedCache.snapshot(site, now)` reads cached data without fetching. Use one `FeedCache` per feed, so one outage never marks another feed stale.

Adapter rules:

- `sites` is anything with `id`, `lat`, and `lon` (`SiteLike`): a DB `Site`, a `SiteSummary`, or a test stub.
- On success with nothing found (no storms, no earthquakes), return one explicit "none" Observation with `value=None` and a clear `label`. Never return an empty list, because empty can't be told apart from a failure.
- Skip null source values. Never write them as zero.
- Label replayed or fixture data `simulated=True` with `data_state="simulated"`.
- Use `httpx` for HTTP. It's already a runtime dependency. `google-genai` is only for Gemini calls.
- Adapters don't write to the database. The caller stores the returned Observations.
- Tests never hit the network. Serve canned source JSON through `httpx.MockTransport`, following `backend/tests/nws_fakes.py`.
- Settings come from `IngestionSettings` (`backend/app/ingestion/settings.py`). Add new feed variables there and to `backend/.env.example`.

- Crew can report a broken electrical pole, downed line, or on-site fire. These hazards come only from crew reports.
- Crew can acknowledge alerts and submit a photo report that says whether a hazard is present.
- A detected hazard or a crew member marking a hazard present sends “potential {hazard}” with no instructions to teams and supervisors inside the Gemini radius.
- Each notified organization's supervisor confirms it for their organization. That organization's teams inside the radius then receive the instruction that supervisor accepted or edited.
- A supervisor sees the full map and every location with its assigned team, occupied locations first, and makes the final call on that organization’s reports that no hazard is present.
- A confirmed flood shows its expected remaining duration to crew and supervisors in plain words, labeled as an estimate, never an all-clear.
- Gemini briefings cite supplied evidence, state unknowns, validate against schemas, and fall back safely. Gemini never explains or interprets the hazard score.
- Auth0 roles change available actions and backend permissions.
- The interface works on mobile and desktop and includes stale, unavailable, loading, and error states.
- The public README describes data sources, model evaluation and limitations, Gemini safeguards, Auth0 setup, and demo steps.
